## Bug 1: STT-Ausgangsspalte zeigt alten Zustand (Q(t) statt Q(t+1))

### Ursache
In `TruthTableModal.tsx` wurde nach `runOneTick()` die LED-Ausgangsspalte via
`nextBuf.outputs[wire.from.gateId][wire.from.portId]` gelesen. Da `runOneTick()` intern
`evaluate()` mit dem **alten** `customState` aufruft, enthielt `nextBuf.outputs` für
synchrone Gatter noch Q(t). Der neue Zustand Q(t+1) lag nur in `nextBuf.customStates`.

### Betroffene Gatter
D_FF, JK_FF, T_FF, D_FF_R, D_FF_ASSR, REG4, REG8, PIPO4, PISO4, SHIFT4,
BIN_CTR7S, BIN_CTR_99, MS_JK_FF, T_FF_ASSR, JK_FF_ASSR

### Fix
**Datei:** `src/components/panels/TruthTableModal.tsx` (nach Zeile 364)

Nach `runOneTick()` werden alle synchronen Gatter mit dem **neuen** `customState`
erneut evaluiert, sodass `nextBuf.outputs` die korrekten Q(t+1)-Werte enthält:

```typescript
for (const gate of allGates) {
  let def; try { def = gateRegistry.get(gate.typeId); } catch { continue; }
  if (!def.isSynchronous) continue;
  const newCs = nextBuf.customStates[gate.id];
  if (!newCs) continue;
  const reEval = def.evaluate({}, newCs);
  for (const [pid, v] of Object.entries(reEval)) {
    nextBuf.outputs[gate.id][pid] = v;
  }
}
```

Das ist analog zu dem, was der `EventScheduler` (Zeile 483-498 in `eventScheduler.ts`)
bereits für den Free-Running-Modus macht.

### Nicht betroffen
- Free-Running-Simulation (EventScheduler re-evaluiert bereits korrekt)
- Kombinatorische Schaltungen (keine stateUpdate-Phase)
- SR-Latch (nicht synchron, Ausgang direkt propagiert)

## Bug 2: Counter-Zustand als einzelnes Integer in STT

### Ursache
`BIN_CTR7S` und `BIN_CTR_99` verwendeten `stateKeys: ['count']`, wobei `count` ein
Integer (0-15 bzw. 0-99) ist. Die STT-Enumeration behandelt jeden `stateKey` als
einzelnes Binärbit (0 oder 1). Dadurch wurden nur 2 Zustände (count=0,1) enumeriert
statt aller 16 bzw. 100 Zustände.

### Fix
**Datei:** `src/gates/sequential/binCounter.gate.ts`

`stateKeys` in individuelle Bits zerlegt:
- `BIN_CTR7S`: `['cnt0', 'cnt1', 'cnt2', 'cnt3']` (4 Bits, 16 Zustände)
- `BIN_CTR_99`: `['cnt0', 'cnt1', 'cnt2', 'cnt3', 'cnt4', 'cnt5', 'cnt6']` (7 Bits)

Hilfsfunktionen `ctr16FromState()` / `ctr16ToState()` und `ctr100FromState()` /
`ctr100ToState()` rekonstruieren den Integer-Wert aus Einzelbits und umgekehrt.

`count` wird weiterhin in `customState` gespeichert (Backward-Kompatibilität +
7-Segment-Shape-Rendering), aber nicht mehr als STT-Variable verwendet.

**Auswirkung auf STT:**
- `BIN_CTR7S`: 4 state + 3 input = 7 Variablen → 128 Zeilen (Limit: 256)
- `BIN_CTR_99`: 7 state + 3 input = 10 Variablen → 1024 → "zu viele" angezeigt
  (korrekt, da 100-Zustände-Tabelle nicht sinnvoll darstellbar)

## Bug 3 (False Positive): PISO4 HDL-Export

### Analyse
Der Report meldete: "Simulator verwendet `bit0` als Ausgang `q`, HDL treibt `q` von `bit3`."

Nach Prüfung ist dies **kein Bug**. Die Zuordnung ist:
- Simulator: `q = bit0` (MSB-Ende der internen Schiebekette)
- Verilog: `q = sr[3]` (MSB des 4-Bit-Registers)
- VHDL: `q = sr(3)` (MSB des 4-Bit-Registers)

Der Verilog-Concat `{p0, p1, p2, p3}` platziert `p0` auf `sr[3]` (MSB).
Im Simulator ist `bit0 = p0` nach dem Laden. Beide geben in derselben
Reihenfolge aus. Das Verhalten ist konsistent.

## Validation Report 2: STT stateKeys für 74xx-ICs und nicht-synchrone Latches

Datum: 2026-03-07

### Ursache

Die STT (Zustandsübergangstabelle) konnte bei mehreren Gattertypen keine korrekten
Zustandsvariablen ableiten:

1. **Nicht-synchrone Latches (SR_LATCH, D_LATCH):** `feedbackGateIds` erkannte nur
   `isSynchronous`-Gatter. SR_LATCH und D_LATCH haben `stateUpdate` aber kein
   `isSynchronous`, weshalb sie nie als Zustandsvariablen aufgenommen wurden.

2. **74xx-ICs mit gepacktem Integer-Zustand:** 74HC161, 74HC163, 74HC194, 74HC373,
   74HC374, 74HC595 speicherten ihren Zustand als gepacktes Integer (`cnt`, `reg`,
   `latch`). Die STT enumeriert jeden `stateKey` als Binärbit (0/1), weshalb gepackte
   Integers nur 2 statt der korrekten Anzahl Zustände erzeugten.

3. **Fehlende explizite `stateKeys`:** 74HC74 hatte keine `stateKeys`-Deklaration,
   obwohl es bereits individuelle Bits (`q1`, `q2`) intern verwendet.

### Fixes

**Datei: `src/components/panels/TruthTableModal.tsx`**
- `feedbackGateIds` erkennt jetzt auch Gatter mit `def.stateUpdate` (nicht nur `isSynchronous`)
- `stateVars` prüft `def.stateKeys` zuerst (auch für nicht-synchrone Gatter)

**Datei: `src/gates/sequential/flipflops.gates.ts`**
- SR_LATCH: `stateKeys: ['q']` hinzugefügt
- D_LATCH: `stateKeys: ['q']` hinzugefügt

**Datei: `src/gates/ic74xx/ic74xx.gates.ts`**
- Generische Hilfsfunktionen: `bitsFromState()`, `bitsToState()`, `makeStateKeys()`
- 74HC74: `stateKeys: ['q1', 'q2']`
- 74HC595: `stateKeys: makeStateKeys('q', 8)` + evaluate/stateUpdate mit `bitsFromState`/`bitsToState`
- 74HC161: `stateKeys: makeStateKeys('cnt', 4)` + evaluate/stateUpdate decomposed
- 74HC163: `stateKeys: makeStateKeys('cnt', 4)` + evaluate/stateUpdate decomposed
- 74HC194: `stateKeys: makeStateKeys('q', 4)` + evaluate/stateUpdate decomposed
- 74HC373: `stateKeys: makeStateKeys('q', 8)` + evaluate/stateUpdate decomposed
- 74HC374: `stateKeys: makeStateKeys('q', 8)` + evaluate/stateUpdate decomposed

Alle ICs behalten den gepackten Legacy-Key (`cnt`, `reg`, `latch`) in `customState`
für Backward-Kompatibilität mit Shape-Rendering.

### Informational (kein Fix nötig)

- **PISO4 HDL-Export:** Bereits in Report 1 als False Positive klassifiziert
- **Tri-State HDL (74HC595, 74HC373, 74HC374):** Syntaktisch korrekt, FPGA-Synthese
  mappt auf Mux-Logik — kein Fehler im Simulator
- **ui-limit:** Schaltungen mit >8 Variablen werden korrekt als "zu viele" angezeigt

### Verbleibender Befund: Tri-State OE HDL-Export

**Betroffene ICs:** 74HC595, 74HC373, 74HC374

**Befund:** Simulator treibt Ausgänge auf `0` wenn /OE inaktiv (high),
HDL-Export erzeugt `Z` (high-impedance) für dieselbe Bedingung.

**Bewertung: Architektonische Limitierung, kein Bug.**

Der Simulator arbeitet mit einem strikten binären Signalmodell (`0 | 1`).
High-Impedance (`Z`) kann im Signalpfad nicht dargestellt werden. Die Konvention
ist dokumentiert in `src/gates/definitions/tristate.gate.ts:6`:
```
// Tri-State Buffer: /OE=0 → Y=A;  /OE=1 → Y=0 (Hi-Z represented as 0)
```

Der HDL-Export erzeugt das **elektrisch korrekte** Verhalten:
- Verilog: `assign q = oe ? 1'bz : latch[i];`
- VHDL: `q <= 'Z' when oe = '1' else latch(i);`

Würde der HDL-Export stattdessen `0` ausgeben, wäre der Export für
Hardware-Synthese falsch — ein aktiver Low-Treiber ist etwas anderes als
ein hochohmiger Ausgang. FPGA-Synthesizer (Yosys, Vivado) mappen interne
Tri-State-Signale automatisch auf Mux-Logik, sodass der exportierte HDL-Code
synthesefähig bleibt.

**Kein Code-Fix erforderlich.** Die Diskrepanz ist ein bekannter Trade-off
zwischen Simulator-Darstellung und HDL-Korrektheit.

## Fix 5: Tri-State OE — Z-Support im Simulator

Datum: 2026-03-07

### Ursache

Der Simulator konnte nur binäre Signalwerte (0/1) darstellen. Bei deaktiviertem OE
lieferten 74HC595, 74HC373, 74HC374 und TRIBUF den Wert `0`, während der HDL-Export
korrekt `Z` (high-impedance) erzeugte. Dadurch waren Simulator und HDL-Export
semantisch inkonsistent.

### Design-Entscheidung: Ultra-minimales Z mit Input-Sanitization

**Kernprinzip:** Z propagiert auf Wires und Outputs. Bevor ein Gate-`evaluate()`
aufgerufen wird, werden Z-Werte zu 0 konvertiert (Pull-Down-Semantik). Damit sehen
bestehende Gates **NIEMALS** den Wert 2 — alle Bitwise-Ops (`XOR`, `AND`, `OR`)
bleiben unverändert und sicher.

### Typänderung

**`src/core/types.ts`**
```typescript
export type SignalValue = 0 | 1 | 2;
export const HI_Z: SignalValue = 2;
```

### Gate-Evaluate-Änderungen

**`src/gates/ic74xx/ic74xx.gates.ts`**
- 74HC595: `evaluate()` gibt `{q0:2,...,q7:2}` zurück bei OE inaktiv (statt 0)
- 74HC373: gleich
- 74HC374: gleich

**`src/gates/definitions/tristate.gate.ts`**
- TRIBUF: `evaluate()` gibt `{y: 2}` zurück bei OE inaktiv (statt 0)

### Input-Sanitization (Pull-Down)

In allen drei Simulation-Engines wird Z beim Lesen von Gate-Inputs zu 0 konvertiert:
- `src/core/simulation/tickEngine.ts` (runOneTick Phase 1)
- `src/core/simulation/eventScheduler.ts` (_evaluateGateWithCs)
- `src/core/simulation/engine.ts` (runSimulation)

```typescript
// Sanitize hi-Z (2) → 0 so gate evaluate functions only see 0|1
inputValues[inp.id] = (raw === 2 ? 0 : raw) as SignalValue;
```

### STT Re-Evaluation Fix

**`src/components/panels/TruthTableModal.tsx`**
- Die Re-Evaluation synchroner Gatter nach `runOneTick()` übergibt jetzt die
  echten Input-Werte (z.B. OE) aus dem Wire-Map statt `{}`
- Damit zeigt die STT korrekt Z wenn OE=1, und Register-Werte wenn OE=0

### UI-Darstellung

Z-Werte werden in der gesamten UI als Amber (#f59e0b) dargestellt:
- **CanvasWire:** Amber-farbene Drähte bei Z
- **OutputLedShape:** Amber-farbene LED bei Z
- **GateBase PortDots:** Amber-farbene Port-Punkte bei Z
- **FlipFlopShape:** Amber-farbene Output-Labels bei Z
- **TruthTableModal:** 'Z' statt '2' in Zellen, Amber-Schriftfarbe
- **TimingDiagram:** Gestrichelte Amber-Linie auf Mittelhöhe für Z

Die Farbe war bereits in `constants.ts` als `SIGNAL_UNKNOWN_COLOR` vorbereitet.

### Regressions-Sicherheit

- Downstream-Gates bekommen nur 0/1 (Input-Sanitization)
- Alle bestehenden `?? 0` Defaults sind semantisch korrekt (Z wäre truthy, wird aber nie an Gates übergeben)
- Alle `as 0 | 1` Casts in bestehenden Gates sind sicher (sehen nie Z)
- Alle XOR/AND/OR Bitwise-Ops sind sicher (empfangen nie Z)
